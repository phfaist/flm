# The npm workspace of the repository (`npm/`)

This folder holds the development tooling of the FLM repository that runs under Node:

- the builds of the files that two of the repository's extensions carry ready-made (the
  stylesheet and script of the lecture-notes page, the MathJax bundle);
- the TypeScript check of `flm-ext/flm.d.ts`, the declarations of the interface that FLM
  gives extensions written in JavaScript.

Nothing in this folder is needed to build or install the `flm` program. The files the
builds write are committed in the extensions' folders, and `cargo build` and `cargo
install` read them as they are. Node is needed only to change the sources of those files,
or to run the checks described below.

The folder is one npm *workspace*: `package.json` lists three *members*, one per
subfolder (`lecturenotes`, `math-mathjax`, `flm-ext`), and npm installs the development
dependencies of all three together.

## Installing the tools

The tools need Node (version 22 or later) and npm. Install them once, in `npm/`:

```text
cd npm
npm install
```

npm installs every member's development dependencies into one folder,
`npm/node_modules/`, as one lock file, `npm/package-lock.json`, records them. Each
dependency has one pinned version, shared by the members that use it: `esbuild` 0.28.2,
`typescript` 7.0.2 and `@mathjax/src` 4.1.3. The lock file is committed; git ignores
`npm/node_modules/` and each member's `target/` folder (where a member stages its outputs
and compiles its tests).

## Building and testing

In `npm/`:

```text
npm run build                       # every member that has a build: lecturenotes, math-mathjax
npm run build -w lecturenotes       # one member, given by its folder
npm test                            # every member that has tests: lecturenotes, flm-ext
npm test -w flm-ext                 # one member: the TypeScript check
```

A member's script also runs from inside its folder: `node build.mjs` in `lecturenotes/`,
`node bundle.mjs` in `math-mathjax/`.

A build writes its outputs into the extension that ships them, under the repository's
`extensions/` folder. The outputs are committed: after a change to a member's sources,
rebuild and commit the outputs with the sources. A build of unchanged sources writes the
committed files byte for byte, so `git status` shows no change after it.

## `lecturenotes`: the lecture-notes page's stylesheet and script

The member `lecturenotes` (package name `flm-lecturenotes`, not published) builds the
stylesheet and the script of the lecture-notes page, the compose template of the extension
`extensions/data/lecturenotes/`. Its sources are under `src/` (TypeScript modules, and the
stylesheet's CSS files under `src/style/`), its unit tests under `test/`, and its build is
`build.mjs`.

`npm run build -w lecturenotes` (or `node build.mjs` in the member) type-checks the
sources, then writes two files into the folder `dist/` of the compose template,
`extensions/data/lecturenotes/templates/html/lecturenotes/dist/`:

- `lecturenotes.js`, the script, one bundle that defines the global name
  `flmLecturenotes`;
- `lecturenotes.css`, the stylesheet, the files of `src/style/` joined in a fixed order.

Each file begins with the line `Generated by npm/lecturenotes (node build.mjs); do not
edit.` The script's source map stays in the member's `target/staging/`, and the script
holds no link to it. `node build.mjs --out DIR` writes the two files into `DIR`.

What checks the member:

- `npm test -w lecturenotes` runs the unit tests with Node's test runner;
- the test `the_committed_bundle_matches_a_fresh_build` of `flm-cli/tests/lecturenotes.rs`
  builds the member into a temporary folder and compares both files with the committed
  ones byte for byte (it is skipped, with a message, when `node` is not on the `PATH` or
  the workspace's dependencies are not installed);
- the test `the_description_s_delimiters_are_those_the_bundle_s_build_checks` of the same
  file checks that the delimiters `build.mjs` refuses in its outputs are the `delimiters`
  of the compose template's description;
- the browser check `check/check.py` renders two documents with the extension and checks
  the page in Google Chrome; it is run by hand, and its opening comment says how.

The extension's `README.md` (`extensions/data/lecturenotes/README.md`) describes the page,
the markup the script expects and its setup function.

## `math-mathjax`: the MathJax bundle

The member `math-mathjax` (package name `flm-math-mathjax-bundle`, not published) builds
the copy of MathJax that the extension `extensions/js/math-mathjax/` carries. `entry.mjs`
is the bundle's source: the parts of MathJax the extension uses, gathered in one object.
`bundle.mjs` bundles it with esbuild.

`npm run build -w math-mathjax` (or `node bundle.mjs` in the member) writes two files into
`extensions/js/math-mathjax/vendor/`:

- `mathjax.js`, the MathJax bundle, one minified ES module;
- `bundle.js`, the list of the MathJax TeX packages the bundle holds, and the MathJax
  version.

Each file begins with a line naming `npm/math-mathjax/bundle.mjs` and the MathJax version
it was built from. The two files are committed; no test rebuilds them. The extension's
tests in `flm-cli` and `flm-ext` run the committed bundle. The browser tests of
`flm-main/tests/watch_page.rs` also load MathJax's own browser files from
`npm/node_modules/@mathjax/src/bundle/`, and a case that needs them is skipped, with a
message, when they are not installed.

The extension's `README.md` (`extensions/js/math-mathjax/README.md`) lists what the bundle
holds.

## `flm-ext`: the TypeScript check of the extension interface's declarations

The crate `flm-ext` provides the interface that FLM gives extensions written in
JavaScript. Its tests generate `flm-ext/flm.d.ts`, the TypeScript declarations of that
interface, which an extension author's editor reads; the file stays in `flm-ext/`.

The member `flm-ext` checks the declarations: its script `test` (`npm test -w flm-ext`,
or `npm test` with the other members' tests) runs the TypeScript compiler over the
project `tsconfig.json`, which holds `flm.d.ts` and two extensions of `flm-ext`'s tests,
`flm-ext/tests/js/lowerjs/main.js` and `flm-ext/tests/js/wordcount/main.js`, checked as
JavaScript against the declarations. A
method these extensions call with a wrong name or a wrong number of arguments fails the
check. The Rust test `flm-ext/tests/typescript_check.rs` runs the same check:

```text
FLM_TESTS_TYPESCRIPT=1 cargo test -p flm-ext --test typescript_check
```

Without `FLM_TESTS_TYPESCRIPT=1`, without `node`, or without the workspace's compiler, the
test writes a line beginning `skipped:` and passes.

The member is named after the crate because a package of the declarations for extension
authors, published on the npm registry, would be made from this folder: by adding the
package's metadata to `package.json` and copying `flm.d.ts` into the folder at build.
Nothing is published from the workspace.
