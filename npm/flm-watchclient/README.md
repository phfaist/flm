# `flm-watchclient`: the watch client of the live preview

While the `flm` program runs `flm watch`, it builds a document into an HTML page again
after each change of its files, and serves the page to a browser on the same machine. The
*watch client* is what runs in the browser, in two parts:

- the *page script*, with its stylesheet, which the document's page carries. It keeps the
  page in step with the document: after each build it updates the parts of the page that
  changed, or loads the page anew, and shows the reader what changed. It marks the
  elements in which the last build's problems lie, and opens the place of an element
  clicked with Ctrl or Cmd and Shift in an editor. It adds no visible element to the page;
- the *tools page*, a page of the preview's server, which shows the document's page in a
  frame beside the preview's tools: a status bar, and a panel with the problems, the
  outline, the help pages, the forms that change the document's front matter, the
  export and the viewer settings. The two parts exchange messages when the page is in
  that frame.

This package builds the watch client into the files that the crate `flm-host` embeds in
the program. Its build is a member of the npm workspace of the repository (`npm/`, see
[`npm/README.md`](../README.md)). The package is not published.

## What the package holds

- `src/`: the sources, in TypeScript (strict). `src/page/` holds the page script and its
  stylesheet `page.css`; `src/tools/` the tools page (`index.html`, the Preact
  application, its stylesheet `tools.css`), with its state in `state/`, its controls in
  `controls/`, the panel's tabs in `panels/` and its output views in `views/`;
  `src/shared/` what both use: the server's addresses and the stream's messages
  (`protocol.ts`), the messages between the two parts (`messages.ts`), and the types of
  the server's answers. The opening comment of each file says what it does.
- `test/`: the tests of the tools page's state, run with node's test runner.
- `build.mjs`: the build and the tests. Its opening comment lists the built files.
- `PROTOCOL.md`: the specification of what the watch client expects of the page that
  carries the page script and of the server that serves it: the messages the server
  sends, the requests it answers, the markup of the page that the page script reads, and
  the messages between the two parts. The server of the `flm` program
  (`flm_host::watch::server::Server`) follows it, and so must any other server that runs
  the watch client.

## The built files and how `flm watch` serves them

The build writes these files into the folder `flm-host/src/watch/client/`, where they are
committed:

- `flm-watchclient.js`, the page script: one script that runs inside one function and
  defines no global name, with the library `morphdom`. The page carries it as a classic
  script (`<script>`), with no module loader;
- `flm-watchclient.css`, the page script's stylesheet;
- `tools/index.html`, `tools/tools.js` and `tools/tools.css`: the tools page, its script
  (with Preact, its signals, highlight.js, ansi_up and the icons it uses) and its stylesheet;
- `tools/pdfjs/`: the files of the library `pdfjs-dist` that the tools page loads when it
  shows a PDF file, and only then: `pdf.min.mjs` and `pdf.worker.min.mjs`, the library and
  its worker, each a module; and, under `standard_fonts/`, `FoxitSymbol.pfb` and
  `FoxitDingbats.pfb`, the fonts that pdf.js draws a PDF's Symbol and ZapfDingbats with
  when the file does not hold them (for the other standard fonts, it uses the browser's),
  with their licenses in `LICENSES.txt`.

Each file but the fonts begins with the line `Generated by npm/flm-watchclient (node
build.mjs); do not edit.`, in a comment (as plain text in `LICENSES.txt`). The next lines
of each script hold the licenses of the libraries it holds, each with its version; those
of `tools.css` hold the license of pdf.js, whose stylesheet its rules of the text layer
are adapted from. Nothing that the build bundles is minified; the files of pdf.js are
copied as the package ships them, after that header, in their minified form, which takes
half the room of the other (about 0.5 MB compressed in all).

The crate `flm-host` includes the page script and its stylesheet in the program (the
constants `SCRIPT_TEXT` and `STYLE_TEXT` of `flm_host::stdpkg::preview`), each after a first
line that holds its identifier: `/* flm.preview.script */` and `/* flm.preview.style */`.
Every build of `flm watch` writes both into the page, and the server's waiting page (the
page it serves before a build has given an output) carries them too. The files of
`tools/` are compressed with gzip when the program is built, embedded, and served under
`/.flm-preview/` (`PROTOCOL.md`, section "The tools page").

## Building

The build needs Node (version 22 or later). Install the workspace's packages once, in
`npm/` (see [`npm/README.md`](../README.md)):

```text
cd npm
npm install
```

Then build, in `npm/`:

```text
npm run build -w flm-watchclient
```

or, in this folder, `node build.mjs`. The build checks the types (`tsc --noEmit`), then
bundles the scripts with esbuild. `node build.mjs --out DIR` writes the files into `DIR`
instead.

After a change to the sources, build and commit the built files with the sources: `cargo
build` reads the committed files and never runs the build. A build of unchanged sources
writes the committed files byte for byte.

## The libraries

The built files hold eight libraries from the npm registry, each at one version: the seven
that `package.json` pins, and `@preact/signals-core`, on which `@preact/signals` depends.
The workspace's lock file, `npm/package-lock.json`, records the version and the checksum
of each. The header of each built file names the libraries it holds, with their versions
and licenses, and holds the text of each license:

| Library | Version | License | Built files that hold it |
|---|---|---|---|
| `morphdom` | 2.7.8 | MIT | `flm-watchclient.js` |
| `preact` | 11.2.0 | MIT | `tools/tools.js` |
| `@preact/signals` | 2.11.4 | MIT | `tools/tools.js` |
| `@preact/signals-core` | 1.14.5 | MIT | `tools/tools.js` |
| `lucide-static` | 1.73.0 | ISC | `tools/tools.js` |
| `highlight.js` | 11.11.1 | BSD-3-Clause | `tools/tools.js` |
| `ansi_up` | 6.0.6 | MIT | `tools/tools.js` |
| `pdfjs-dist` | 6.5.438 | Apache-2.0 | `tools/pdfjs/pdf.min.mjs`, `tools/pdfjs/pdf.worker.min.mjs`, and `tools/tools.css`, whose rules of the text layer are adapted from the library's stylesheet |

The two fonts of `pdfjs-dist`, `tools/pdfjs/standard_fonts/FoxitSymbol.pfb` and
`FoxitDingbats.pfb`, carry the license of their authors, the PDFium authors (BSD-3-Clause),
in `tools/pdfjs/standard_fonts/LICENSES.txt`.

What each library does:

- **`morphdom`** changes an element into another while keeping every element that is the
  same in both, which the page script uses to update a changed part of the page in place.
- **`preact`** is the library of the tools page's user interface.
- **`@preact/signals`** and **`@preact/signals-core`** hold the values of the tools
  page's state, which the interface follows.
- **`lucide-static`** is the icons of the Lucide set as SVG files. The build bundles the
  text of each icon the tools page imports into its script (`import check from
  'lucide-static/icons/check.svg'`), without the file's comment.
- **`pdfjs-dist`** is pdf.js, which draws the pages of a PDF file and the text layer that
  lets their text be selected.
- **`highlight.js`** highlights the syntax of a text; the tools page bundles its core and
  its LaTeX grammar alone, with which the text view highlights a LaTeX output.
- **`ansi_up`** turns the escape sequences of a terminal's colors and styles into HTML,
  with which the text view shows a text output that holds them, such as that of the build
  type `tty`.

None of them defines a global name or changes a built-in object of the document's page.
pdf.js, loaded into the tools page alone, defines the global names `pdfjsLib` and
`_pdfjsTestingUtils` there. To change a library's version: set the version in
`package.json`, run `npm install`, then the build and the tests in `npm/`, and run the
browser tests (below). For `pdfjs-dist`, check that the files that `PDFJS` of `build.mjs`
names are still the ones the library loads.

## What checks the package

- `npm test -w flm-watchclient` (in `npm/`), or `node build.mjs test` in this folder,
  compiles the tests of `test/` with esbuild and runs them with node's test runner.
- The test `the_committed_bundle_matches_a_fresh_build` of `flm-host/tests/watch_client.rs`
  builds the package into a temporary folder and compares every built file with the
  committed one byte for byte. It is skipped, with a message, when `node` is not on the
  `PATH` or the workspace's packages are not installed.
- The browser tests of `flm-host/tests/watch_page.rs` run the page script and the tools
  page in Google Chrome without a window, against the server of the `flm` program and
  against messages of their own making. One of them checks that the page script defines
  no global name and changes no built-in object.

  ```text
  FLM_TESTS_BROWSER=1 cargo test -p flm-host --features watch,js --test watch_page
  ```

  Without `FLM_TESTS_BROWSER=1`, or when Chrome is not found, each test writes a line
  beginning `skipped:` and passes. `FLM_TESTS_CHROME` names the program of Chrome or
  Chromium to use.
